# Inspection and assurance

**Product direction reviewed 11 November 2026**

Graiphic Studio is Graiphic's proprietary engineering environment built on the open FROG language. Its objective is to help you understand consequential behavior, investigate an unexpected result and carry a valid correction into the version you run or build. The same objective applies to human-authored programs and proposals generated by an agent.

## What the views and tools tell you

The Block Diagram exposes dependencies, structures and state. Source exposes the saved document. Run and Highlight show behavior within a supported execution profile. Build produces an artifact for a supported target, with its declared dependencies.

These tools answer related but different questions:

| Tool or evidence | What it can establish |
| --- | --- |
| Graph and Source inspection | The represented structure and the logic relevant to the question you are investigating. |
| Language validation | Whether the document satisfies the applicable structural and semantic rules. |
| Target admission | Whether the chosen backend and providers support the complete program. |
| Run, Highlight and tests | What happened in the identified run and whether the tested expectations were met. |
| Build | Whether that captured program could be compiled and packaged for the chosen configuration. |
| A future formal-verification integration | A stated property for the model or artifact actually checked, under explicit assumptions. This is a research direction, not a released Studio feature. |

A readable diagram does not prove that its algorithm meets your requirement. A successful build does not establish that the application ran correctly. A successful test covers its stated conditions. Highlight helps explain an execution; it is not a mathematical proof or a target timing measurement.

## Coverage and current limits

Normal execution, Highlight and LLVM/native compilation are available for selected functions and profiles. The demonstrated native path is Windows on x86-64. Check the relevant function documentation, Run/Build diagnostics, example profile and attributed checkpoint rather than inferring support from an icon or a palette entry.

Source syntax, serialization/profile documentation and Studio development continue. Public FROG Source and Studio authoring documents have explicit compatibility boundaries. General imports from C, C++, Rust, JavaScript or Java, and deployment to additional processor or hardware families, must not be assumed.

No FROG/Studio-to-Verus integration, whole-language verification or comparative human-performance result is established by this documentation update. It adds no verifier command or new execution mode.

## Keep the result connected to its evidence

Review the version actually built and run. Record the relevant inputs, dependencies, configuration and expected result. Observations from a previous version can guide an investigation but do not establish the behavior of a modified program. Source mappings and fingerprints identify artifacts; they do not prove that a translation preserves their meaning.

When a future verifier is integrated, its result will need to identify the property, assumptions and checked artifact. A proof of exported Rust would not automatically verify a separate Studio LLVM binary. Failed, unsupported, inconclusive and stale results need distinct treatment.

## Research and further reading

The proposed research question is whether the dataflow view helps engineers diagnose a broken property and make a valid repair, compared with a workflow given the same requirements, contracts and verifier information. Comprehension, correctness and mistaken confidence matter alongside elapsed time. A compact overview or source-line count alone does not establish the benefit.
